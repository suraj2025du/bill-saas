## R2: a second tab or window reissued invoice numbers and overwrote newer records

**What was wrong.** Each tab or window saved from the copy of the data it loaded at start. A tab left open since the
morning took `INV/26-27/0001` again after another tab had issued it, wrote back its old copy of the business record
(reverting series, bank accounts and other settings changed elsewhere), overwrote records edited in the other tab, and
two tabs opened together both created the due recurring copies.

**Reproduced.** `tests/integration/multi-tab.test.ts` opens two "tabs" (separate connections and separate copies of the
data) on the same storage, in both modes. Before the fix all 10 first tests failed: the stale tab's save went through
("promise resolved instead of rejecting"), in IndexedDB and on the local server alike.

**Root cause.** The store assumed it was the only writer. Storage applied puts by id with no version check (last
writer wins), numbering ran against the tab's own copy, and a number typed by hand did not touch the business record,
so nothing tied number claims together across tabs.

**Fix.** Optimistic concurrency per record, in both storage modes. A single-writer lock (Web Locks) was not used,
because a second browser on the same server shares no lock with the first.
- Every write in a batch carries `base`: the `updatedAt` of the record in the tab's data when the batch is made (null
  when the tab has no such record). `store.commit` takes these versions at call time, so a batch queued behind another
  save, or behind a reload, cannot pass as based on data it never saw.
- `FileStore.commit` (server) and `IndexedDbAdapter.commit` (inside the same read-write transaction, which IndexedDB runs
  one at a time across tabs) compare them with the stored records and refuse the whole batch on any mismatch
  (`ConflictError`, HTTP 409). `validateBatch` checks the `base` values.
- On a conflict the tab loads the latest data and shows "Another tab or window saved changes first, so this was not
  saved. The latest data is now loaded: check it and save again." (`StaleDataError`). Saving again works from the new data.
- Save actions refuse a screen's older copy of a record when the tab now holds a newer one ("This record changed after
  you opened it..."), so a stale editor cannot overwrite after the reload. The business profile form keeps the copy it
  saved, so saving it twice still works.
- A number typed by hand now also writes the business record, as an automatic number already did, so two tabs cannot
  both claim a number.
- Start-up housekeeping (trash clean-up, recurring invoices, daily backup) that another tab already did is skipped
  without a message.
- `nowISO()` never returns the same time twice in a tab, so every save gives a record a new version.

## R3: a server save that failed half-way was lost after the next save and a restart

**What was wrong.** When a data file could not be replaced (antivirus or an indexer holding `clients.json`, a full
disk), the save returned 500 but the server's memory kept the change. The next successful save replaced `journal.json`
and wrote only its own collections, so after a restart the record was gone.

**Reproduced.** `tests/integration/server.test.ts`, "writes the waiting batch before the next save, so a later save
does not drop it" (the review's scenario, a folder in place of `clients.json`) failed with
`expected [] to deeply equal [ 'Saved during a lock' ]`: 0 parties after the restart.

**Root cause.** `FileStore.commit` changed memory before the data files were written, and treated `journal.json` as a
single slot that the next save overwrote and deleted.

**Fix.** The journal is the commit point. Memory changes only after the batch's journal is on disk (a failure before
that changes nothing). If a data file then cannot be written, the batch waits in the journal and in memory, and the save
is reported as saved (it is on disk and is replayed at start). The next save first writes the waiting batch to its data
files and is refused while that still fails, so a journal is never replaced before its batch is in the data files.
Removing the journal after a save is best effort (a leftover journal holds the latest batch, and replaying it is harmless).
A restore clears the waiting batch, because it replaces the data folder as a whole. Memory updates now reuse
`applyBatch` from `src/data/apply.ts` instead of a second copy of that code.

**Files changed.** `server/fileStore.ts`.

**Regression tests.** `tests/integration/server.test.ts`, "a save that fails half-way (review R3)": "keeps a batch whose
data file could not be written in the journal and in memory"; "writes the waiting batch before the next save, so a
later save does not drop it"; "refuses later saves while the waiting batch still cannot be written, and keeps it";
"changes nothing when the journal itself cannot be written" (a guard that already passed before the fix).

## Y11: restoring a large backup failed at the 50 MB request limit

**What was wrong.** Every API request, restore included, was limited to 50 MB, and the Restore button of a listed
backup downloaded it to the browser and posted it back. With purchase-bill photos inside the data, a backup over 50 MB
could not be restored from the app.

**Reproduced.** `tests/integration/server.test.ts`: "restores a backup file over 50 MB" (a 54 MB backup with 14 bill
photos) got HTTP 413, and the in-place restore route did not exist (404).

**Root cause.** One `express.json({ limit: '50mb' })` for all routes, and the in-app restore of a listed backup sent the
whole backup through it.

**Fix.**
- `POST /api/backups/:id/restore` restores a backup from the backup folder on the server (id pattern check, full
  integrity check, pre-restore backup first), so it never travels through a request. In browser mode
  `IndexedDbAdapter.restoreBackup` does the same inside IndexedDB. The Backup screen uses this for every listed backup.
- `/api/restore` (Restore from file) accepts up to 500 MB, under the ~512 MB a JavaScript engine can hold as one JSON
  string, so every backup this app writes can be restored. Every other request keeps 50 MB, and the error names the
  limit of the route that refused it.
- The Backup screen refuses a file over 500 MB before reading it (server mode) and warns once the backups pass 80% of
  the limit.

**Files changed.** `server/app.ts`, `src/data/http.ts`, `src/data/adapter.ts`, `src/data/indexeddb.ts`,
`src/store/store.ts`, `src/features/settings/DataSettings.tsx`.

**Regression tests.**
- `tests/integration/server.test.ts`, "restoring a large backup (review Y11)": "restores a backup file over 50 MB";
  "restores a server backup in place, so its size never has to fit in a request"; "refuses a missing, invalid or
  damaged server backup and leaves data unchanged"; "keeps the 50 MB limit for ordinary saves and names the limit"
  (a guard that already passed before the fix).
- `tests/integration/adapters.test.ts`: "IndexedDbAdapter > restores a local backup in place and keeps a pre-restore
  backup", "HttpAdapter against the real server > restores a server backup in place (review Y11)".
